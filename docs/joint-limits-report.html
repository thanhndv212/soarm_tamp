                  ├─▶ safe_planning_bounds() ─▶ planner YAML ─▶ HPP plans

                  │
Servo EEPROM   ───┴──────────────────────────────────▶ the servo obeys THIS,
MIN/MAX_ANGLE       (never read by any layer above —      not the clamped value

Layers 5–7 decide what gets planned. Layers 1–3 decide what gets commanded. They meet only at layer 4 — the calibration file. If its tick_min/tick_max don't match what's actually in EEPROM, every layer above plans against a window layer 1 will not actually allow, and nothing compares them.

03

How professional stacks solve this

Not a new problem — the standard failure mode of any motion stack with more than one place that thinks it owns "how far can this joint go." Four ecosystems, checked against this arm's exact situation.

ros2_control

Names the two tiers explicitly — hard limits (physical/firmware) and soft limits (where a controller starts constraining, strictly inside the hard ones). A soft limit outside its hard limit is a load-time config error, not a runtime surprise. enforce_command_limits makes enforcement mandatory, not opt-in.

Nothing here validates layer 5 sits inside layer 1 at load time. unreachable_bounds() is the first check that does — and only for the planner YAML.

Universal Robots

Safety Configuration limits are checksummed, need a safety-system restart to change. If the arm's actual position is outside the configured limit at power-on, the controller enters Recovery and refuses every program until a person moves the arm back in range.

Disagreement between believed and actual state halts, it does not clamp — the pattern behind this session's own _within_servo_limits(), but UR runs it at connection time, not only right before one execute.

Franka Emika

libfranka raises a typed exception on a limit violation, never a print a caller can scroll past. Separately, it refuses to talk to a robot whose firmware version doesn't match what the library expects.

The calibration file is this arm's "compiled assumption" about the servos. This bug is structurally a firmware/library version mismatch — the calibration described a tick frame the servos no longer report in.

MoveIt

joint_limits.yaml is generated as an exact copy of the URDF; a user may only edit it narrower, never wider. One direction is allowed away from the source.

so101.yaml and conventions.URDF_LIMITS are two hand-copies of the same six numbers — identical today by diligence, not by construction. The YAML bound that went wider than the servo (§02) is exactly the forbidden direction.

05

Recommendations

  1. 01
    Fix the gripper the same way as the wrist. Measure the true closed-jaw stop, widen the EEPROM floor just above it, correct the calibration and GRIPPER_CLOSED_DEG to match. The one item here that fails on the next grasp attempt if left alone.
  2. 02
    Move the servo-limit check into execute.py itself so it runs on every path, dashboard or bare CLI — the ros2_control pattern of validation the caller cannot opt out of.
  3. 03
    Run phantom_range() at connection time, not only before execute — the UR pattern. Diff the calibration against the live servos the moment the bus opens, and refuse to proceed on disagreement.
  4. 04
    Collapse the duplicate URDF limit copies into one generated source, the way MoveIt derives joint_limits.yaml from the URDF instead of retyping it.
  5. 05
    Version the calibration against the EEPROM it was measured from — the Franka pattern. Record each joint's servo limits inside the calibration file at ROM-sweep time, so a future check catches "the servo changed since" as well as "the calibration was always wrong."
  6. 06
    Re-run the ROM sweep for elbow_flex in wheel mode, which drives to an actual stall — the only way to settle its 0.95 rad of phantom range, which this session's torque-limited probe could not.
  7. 07
    Adopt the one-directional derivation rule explicitly: any config derived from another may only narrow it, never widen it. unreachable_bounds() already checks this for the planner YAML; worth generalizing to every derived layer in the map above.
